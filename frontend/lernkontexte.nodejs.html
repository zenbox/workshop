      Tag 1 · Node.js & HTTP

      Von der Browseraktion zur ersten Antwort
      1.1

      Health-Check: HTML-Oberfläche spricht den Server an

      Am ersten Tag reicht eine kleine Antwort. Der feste UI-Baustein wird nicht umgebaut; ein JavaScript-Aufruf prüft, ob der Node.js-Server erreichbar ist.

      Browser-JavaScript · fetch
      // UI → GET /api/health
// Tag 1: nativer node:http-Handler liefert zunächst { status: "ok" }.
async function checkBackend() {
  const response = await fetch("/api/health");
  if (!response.ok) throw new Error("Backend nicht erreichbar");
  return response.json();
}
      Backend-AndockpunktGET /api/health wird zuerst im nativen HTTP-Server beantwortet. Später kann derselbe Pfad über Express laufen. Der Health-Check hängt nicht an einer Route für fachliche Daten.
      1.2

      Asynchrone Dateiübung bleibt serverseitig

      Die fs-Übung vermittelt Promises und Fehlerbehandlung. Der Browser greift nie direkt auf Serverdateien zu; ein Backend-Modul führt die Dateioperation aus.

      Node.js-Modul · nicht im Browser
      import { readFile, writeFile } from "node:fs/promises";

// Backend-Modul: wird später von einem Controller
// oder Service aufgerufen, nicht von der HTML-Seite.
export async function readText(path) {
  return readFile(path, "utf8");
}

export async function writeText(path, text) {
  return writeFile(path, text, "utf8");
}
      Backend-AndockpunktAm Kurstag zuerst isoliert ausführen. Wird die Übung über HTTP gezeigt, ruft ein Controller dieses Modul auf und gibt nur eine kontrollierte Antwort zurück. Die eigentlichen Datensätze landen später in SQLite, nicht in Dateien.

      Tag 2 · MVC, CRUD & SQLite

      Dieselbe View erhält echte API-Daten
      2.1

      Route → Controller → Model: Liste laden

      Der Browser kennt nur den API-Vertrag. Express-Routen ordnen Anfragen zu; der Controller koordiniert und das Model liefert Daten.

      Express-MVC · Ausschnitt
      // routes/entryRoutes.js
router.get("/", entryController.list);

// controllers/entryController.js
export async function list(req, res, next) {
  try {
    const entries = await EntryModel.findAll();
    res.json(entries);
  } catch (error) {
    next(error); // zentrale Fehler-Middleware
  }
}

// Browser: GET /api/entries → JSON für die vorhandene Liste
      Backend-AndockpunktMount: app.use("/api/entries", entryRoutes). Die Route bleibt dünn. Der Controller ruft das Model auf und bestimmt die HTTP-Antwort; die bereitgestellte HTML-Datei rendert das zurückgegebene JSON.
      2.2

      Formulare und Aktionen auf CRUD abbilden

      Die vorbereiteten Buttons für Neu, Bearbeiten, Duplizieren und Löschen rufen passende Endpunkte auf. Es ist kein Frontend-Neubau nötig.

      Browser-JavaScript · Request helper
      async function sendJSON(url, method, body) {
  const response = await fetch(url, {
    method,
    headers: { "Content-Type": "application/json" },
    credentials: "same-origin",
    body: body ? JSON.stringify(body) : undefined
  });
  if (!response.ok) throw new Error(`HTTP ${response.status}`);
  return response.status === 204 ? null : response.json();
}

// Create: POST /api/entries
// Update: PATCH /api/entries/:id
// Duplicate: POST /api/entries/:id/duplicate
// Delete: DELETE /api/entries/:id
      Backend-AndockpunktJeder Aufruf landet auf einer gleichnamigen Route. Die Route übergibt an entryController.create/update/duplicate/remove; der Controller prüft Eingaben und ruft die jeweilige Model-Funktion auf. Der Controller gibt passende Statuscodes zurück.
      2.3

      SQLite einsetzen, ohne das Frontend zu ändern

      Das mitgelieferte SQL-Skript legt Tabellen und Beziehungen an. Danach ersetzt das Model die bisherigen Beispieldaten durch Datenbankzugriffe.

      Model · API-Vertrag bleibt stabil
      // models/EntryModel.js
// db ist die im Kurs eingerichtete SQLite-Verbindung.
export function findAll() {
  return db.all(
    "SELECT id, title, category, status, priority, description FROM entries ORDER BY id DESC"
  );
}

// Der Controller wartet mit await auf das Model.
// Die View ruft weiterhin GET /api/entries auf.
      Backend-AndockpunktSQL-Datei: bereitgestellt. Im Kurs wird sie ausgeführt und ihr Schema nachvollzogen. Die Model-Funktionen verwenden parametrisierte Abfragen für Erstellen, Ändern und Löschen. Die Browser-View bleibt unverändert, solange JSON-Form und API-Vertrag gleich bleiben.

      Tag 3 · Anmeldung, Echtzeit & Sicherheit

      Die Anwendung wird nutzerbezogen und live
      3.1

      Login und serverseitige Session

      Die View sendet Zugangsdaten einmal an den Login-Endpunkt. Das Backend prüft das Passwort und setzt ein Session-Cookie; JavaScript liest das Cookie nicht aus.

      Browser-JavaScript · Cookie bleibt HttpOnly
      async function login(email, password) {
  return sendJSON("/api/auth/login", "POST", { email, password });
}

// Geschützte Anfrage: same-origin sendet das Session-Cookie.
const entries = await fetch("/api/entries", {
  credentials: "same-origin"
}).then(response => response.json());
      Backend-AndockpunktPOST /api/auth/login → Auth-Controller → Passwortprüfung → Session-Store. Cookie-Optionen setzt der Server (HttpOnly, SameSite, in Produktion Secure). Auth-Middleware schützt Routen; Models filtern nach der Nutzer-ID aus der Session.
      3.2

      Socket.IO für berechtigte Live-Updates

      Nach einer erfolgreichen Änderung aktualisieren verbundene Browser ihre Liste. Die View fragt die aktuelle Liste neu ab, statt ungeprüfte Daten zu übernehmen.

      Browser-JavaScript · Socket.IO Client
      const socket = io({ withCredentials: true });

socket.on("entry:created", () => loadEntries());
socket.on("entry:updated", () => loadEntries());
socket.on("entry:deleted", () => loadEntries());

// Socket-Verbindung schließen bei Logout:
socket.disconnect();
      Backend-AndockpunktSocket.IO verwendet denselben HTTP-Server und dieselbe Session-Prüfung. Erst nach dem Datenbank-Commit sendet der Controller ein Ereignis. Der Server weist den Socket einem autorisierten Nutzer-Raum zu; der Client bestimmt weder Nutzer-ID noch Raum.
      3.3

      Fehler, Sicherheit und Abschlussprüfung

      Das Frontend zeigt Fehler verständlich an. Verbindliche Validierung, Rechteprüfung und sichere Ausgabe bleiben Aufgaben des Backends.

      Browser-JavaScript · Antwort prüfen
      try {
  const entry = await sendJSON("/api/entries", "POST", formData);
  showMessage("Gespeichert");
} catch (error) {
  // UI-Hinweis ist Komfort, kein Ersatz für
  // Validierung im Controller.
  showMessage("Speichern nicht möglich. Eingaben prüfen.");
}
      Backend-AndockpunktMit `node:test` und Testdatenbank prüfen: gültige/ungültige Eingaben, nicht angemeldet, fremder Datensatz, CRUD und zwei getrennte Sessions. SQL parametrieren, HTML-Ausgabe escapen, Cookie-Auth gegen CSRF absichern und Berechtigungen serverseitig erzwingen.
